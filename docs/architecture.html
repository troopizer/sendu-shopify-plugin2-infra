Staging and Prod AWS Architecture

This document describes the architecture implemented by the CloudFormation templates in staging/template.yaml and prod/template.yaml. The two environments use separate stacks, separate templates, separate parameters, and separate ECR repositories.

Overview

Runtime Request Flow

Public browser traffic enters through API Gateway for the frontend runtime. API traffic is proxied to the backend ALB, which forwards to the Rails ECS service. The backend connects to private PostgreSQL and reads application secrets from Secrets Manager.

The VPC spans two availability zones. Public subnets host the ALB, current ECS tasks, and the SSM-only bastion. Private DB subnets host PostgreSQL. Private app subnets are defined but are not currently used by the ECS service.

Public ingress

The ALB accepts HTTP on port 80 from 0.0.0.0/0. API Gateway fronts the frontend Lambda runtime.

Current ECS placement

The ECS service currently runs in public subnets with public IP assignment enabled, while still only accepting traffic from the ALB security group.

Database isolation

PostgreSQL is private and only allows port 5432 from the backend service security group and the bastion security group.

Deployment

Infra Deployment Lifecycle

This infra repository deploys CloudFormation only. Docker images are built and pushed by the owning application repositories, then this repo deploys those existing ECR image tags to the selected environment.

1

Choose environment

Deploy to staging or prod. Environment defaults can come from .env, exported variables, or explicit Makefile variables.

2

Choose image tags

Use one shared VERSION, choose VERSION=latest, or provide separate BACKEND_VERSION and FRONTEND_VERSION.

3

Run deploy

The Makefile calls scripts/deploy.sh, which validates the template, checks ECR tags, and applies a CloudFormation change set.

4

Verify health

After CloudFormation completes, checks cover ECS stability, ALB target health, Lambda status, HTTP health, and recent diagnostic logs.

Same backend and frontend tag

Use when both runtime images were pushed with the same version tag.

make deploy staging VERSION=<image-tag>
make deploy prod VERSION=<image-tag>

Latest backend and frontend

Use only when the intended deployment is explicitly the latest ECR tag for both images.

make deploy staging VERSION=latest
make deploy prod VERSION=latest

Separate backend and frontend tags

Use when the backend and frontend application repositories produced different image tags.

make deploy staging BACKEND_VERSION=<backend-tag> FRONTEND_VERSION=<frontend-tag>
make deploy prod BACKEND_VERSION=<backend-tag> FRONTEND_VERSION=<frontend-tag>

Bootstrap

Use make bootstrap staging or make bootstrap prod for first-time stack creation. Bootstrap sets BackendDesiredCount=0 and EnableFrontendRuntime=false so ECR repositories can be created before images exist.

Normal deploy

Use make deploy after image tags exist in ECR. Stopped ECS tasks and backend/Lambda warning or error log findings are reported as diagnostics; they do not fail deployment by themselves.
